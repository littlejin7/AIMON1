# AI-MON 데일리·위클리 미션

> 실제 미션 정의, 진척 이벤트, 수동 보상 수령, 저장 구조와 검수 기준을 정리한 현재 구현 문서

---

## 0. 문서 목적

이 문서는 다음을 정의한다.

- 현재 존재하는 데일리·위클리 미션
- 어떤 사용자 행동이 진척으로 인정되는지
- 미션 기간이 언제 바뀌는지
- 보상이 어떤 재화로 지급되는지
- 수동 수령과 중복 지급 방지 방식
- 비로그인 체험의 미션 처리
- 홈 화면 표시와 알림
- 회귀 테스트와 운영 검수 기준

관련 문서:

- 전체 서비스: [`AI_MON_PROPOSAL.md`](./AI_MON_PROPOSAL.md)
- 시스템 흐름: [`AI_MON_PIPELINE.md`](./AI_MON_PIPELINE.md)
- 데이터 구조: [`AI_MON_SCHEMA.md`](./AI_MON_SCHEMA.md)

구현과 문서가 충돌하면 GitHub `main` 브랜치 코드와 `backend/data/missions.json`이 우선한다.

## 1. 현재 구현 요약

| 항목 | 현재 상태 |
|---|---|
| 데일리 미션 | 3종 |
| 위클리 미션 | 3종 |
| 정의 파일 | `backend/data/missions.json` |
| 사용자 진척 | `users.missions` JSONB |
| 진척 방식 | 사용자 행동 발생 시 이벤트 훅 |
| 데일리 기준 | KST 날짜 |
| 위클리 기준 | KST ISO 주차 |
| 기간 초기화 | 접근 시 lazy reset |
| 보상 수령 | 전체 미션 수동 수령 |
| 지급 방식 | 원자적 사용자 갱신 |
| 홈 표시 | `MissionWidget` |
| 수령 가능 알림 | 홈 탭 빨간 점 |
| 별도 초기화 스케줄러 | 사용하지 않음 |
| 비로그인 체험 | 미션 진척·보상 없음 |
| GP 지급 | 현재 미션 정의에는 없음 |
| 레거시 보상 키 | `reward.xp`, `xp_awarded` |

핵심 흐름:

```text
로그인 사용자 행동
  ↓
도메인 라우터가 미션 이벤트 발생
  ↓
bump_mission(user, event)
  ↓
데일리·위클리 정의 확인
  ↓
일치하는 미션 progress 증가
  ↓
사용자가 홈에서 수령하기 클릭
  ↓
POST /missions/claim
  ↓
원자적 완료·중복 검증
  ↓
보상 지급
```

## 2. 미션 정의 스키마

정의 파일:

```text
backend/data/missions.json
```

최상위 구조:

```json
{
  "daily": [],
  "weekly": []
}
```

미션 객체:

| 필드 | 타입 | 설명 |
|---|---|---|
| `mission_id` | string | 전체 미션에서 고유한 ID |
| `title` | string | 화면 표시명 |
| `event` | string | 진척 이벤트 |
| `goal` | integer | 완료 목표 |
| `reward` | object | 보상 정의 |
| `reward.xp` | integer | 레거시 키, 현재 지급 로직에서 코인·누적 랭킹점수로 변환 |
| `reward.coin` | integer | 프론트 표시 지원 가능, 현재 정의에는 없음 |
| `reward.crowns` | integer | 왕관 보상 |
| `auto_claim` | boolean | 레거시 호환 가능, 현재 자동 수령은 사용하지 않음 |

ID 규칙:

```text
d_... = daily
w_... = weekly
```

# Part A. 데일리 미션

## 3. 스테이지 퀴즈 3회 클리어

| 항목 | 값 |
|---|---|
| `mission_id` | `d_quiz3` |
| 표시명 | 스테이지 퀴즈 3회 클리어 |
| 이벤트 | `stage_clear` |
| 목표 | 3 |
| 정의 보상 | `xp: 300` |
| 실제 지급 | 코인 300 + 누적 랭킹점수 300 |
| 왕관 | 없음 |
| GP | 없음 |
| 수령 | 수동 |

```json
{
  "mission_id": "d_quiz3",
  "title": "스테이지 퀴즈 3회 클리어",
  "event": "stage_clear",
  "goal": 3,
  "reward": {
    "xp": 300
  }
}
```

진척 인정:

- 로그인 사용자가 일반 스테이지 퀴즈를 서버 기준으로 클리어
- 서버의 정상 완료 처리까지 성공

진척 미인정:

- 비로그인 체험
- 브리핑만 본 상태
- 로컬 점수만 변경된 상태
- 동일 요청의 중복 완료가 서버에서 차단된 경우
- 미니보스·유닛보스·엔드보스 클리어

# Part B. 위클리 미션

## 6. 보스 2회 처치

| 항목 | 값 |
|---|---|
| `mission_id` | `w_boss2` |
| 표시명 | 보스 2회 처치 |
| 이벤트 | `boss_clear` |
| 목표 | 2 |
| 정의 보상 | `xp: 1500`, 왕관 2개 |
| 실제 지급 | 코인 1,500 + 누적 랭킹점수 1,500 + 왕관 2 |
| GP | 없음 |
| 수령 | 수동 |

```json
{
  "mission_id": "w_boss2",
  "title": "보스 2회 처치",
  "event": "boss_clear",
  "goal": 2,
  "reward": {
    "xp": 1500,
    "crowns": 2
  }
}
```

현재 `boss_clear` 대표 발생 경로:

- 유닛보스 최초 클리어
- 엔드보스 코스별 최초 클리어

스테이지 미니보스는 `miniboss_clear` 이벤트를 사용하므로 `w_boss2`에 포함되지 않는다.

재도전으로 이미 클리어한 보스를 다시 이긴 경우 미션 진척을 올릴지는 각 보스 라우터의 최초 클리어 조건을 따른다. 중복 호출로 두 번 증가하면 안 된다.

# Part C. 기간과 사용자 상태

## 9. 기간 기준

### 데일리

```text
Asia/Seoul 기준 YYYY-MM-DD
```

### 위클리

```text
Asia/Seoul 기준 ISO year + ISO week
```

서버 UTC 날짜를 그대로 사용하지 않는다. 한국 시간 자정 전후에 기간이 잘못 바뀌지 않도록 KST 변환 후 키를 계산한다.

## 10. Lazy reset

미션 기간 초기화는 별도 스케줄러가 아니라 미션 상태 접근 시 수행한다.

```text
현재 기간 키 계산
  ↓
저장된 기간 키와 비교
  ↓
다르면 해당 daily 또는 weekly 상태 초기화
  ↓
현재 요청 처리
```

장점:

- 스케줄러 중복 실행에 의존하지 않음
- 사용자가 실제 접근할 때만 갱신
- 서버 재시작과 무관

주의:

- 초기화와 진척 증가가 한 요청 안에서 일관되게 처리되어야 한다.
- 여러 요청이 동시에 들어와도 새 상태를 서로 덮어쓰면 안 된다.
- 데일리와 위클리는 각각 독립적으로 초기화한다.

## 11. 사용자 미션 상태

개념 구조:

```json
{
  "daily": {
    "period": "2026-07-11",
    "progress": {
      "d_quiz3": 0,
      "d_review": 0,
      "d_login": 1
    },
    "claimed": [],
    "login_days": ["2026-07-11"]
  },
  "weekly": {
    "period": "2026-W28",
    "progress": {
      "w_boss2": 0,
      "w_streak5": 1,
      "w_ai5": 0
    },
    "claimed": [],
    "login_days": ["2026-07-11"]
  }
}
```

정확한 키 구조는 현재 미션 라우터 구현을 우선한다.

저장 원칙:

- 없는 미션 키는 0으로 처리한다.
- 목표를 초과해도 UI 표시 값은 목표 이하로 제한할 수 있다.
- 수령 여부는 진척 값과 분리한다.
- 정의 파일에서 삭제된 미션의 과거 상태가 있어도 오류가 나지 않아야 한다.
- JSONB 전체를 오래된 프론트 상태로 덮어쓰지 않는다.

# Part D. 이벤트 계약

## 12. 이벤트 목록

| 이벤트 | 발생 의미 | 연결 미션 |
|---|---|---|
| `stage_clear` | 일반 스테이지 퀴즈 클리어 | `d_quiz3` |
| `review_done` | 오답 복습 완료 | `d_review` |
| `login` | 로그인·세션 진입 시 출석 처리 | `d_login`, `w_streak5` |
| `boss_clear` | 유닛보스·엔드보스 인정 클리어 | `w_boss2` |
| `miniboss_clear` | 스테이지 미니보스 클리어 | 현재 `w_boss2` 미포함 |
| `ai_feedback` | 실제 AI 피드백 생성 성공 | `w_ai5` |

새 이벤트를 추가할 때:

1. `missions.json` 정의
2. 이벤트 발생 라우터
3. 중복 발생 조건
4. 미션 상태 갱신
5. 프론트 표시
6. 회귀 테스트

를 함께 수정한다.

---

## 13. 이벤트 발생 시점

이벤트는 사용자의 화면 행동이 아니라 서버에서 성공이 확정된 뒤 발생해야 한다.

올바른 순서:

```text
도메인 처리 검증
→ DB 저장 또는 전투 세션 확정
→ 중복 여부 확인
→ 미션 이벤트 발생
→ 미션 상태 저장
→ 응답
```

잘못된 예:

- 문제 제출 버튼을 누르자마자 `stage_clear`
- 보스 승리 애니메이션 시작만으로 `boss_clear`
- AI 요청 시작만으로 `ai_feedback`
- 오답 페이지 진입만으로 `review_done`

# Part E. 비로그인 체험

## 14. 게스트 정책

비로그인 체험은 미션 대상이 아니다.

현재 체험 범위:

- 공개 레슨 목록
- 초급 Stage 1-1
- 개념 퀴즈
- 80점 이상 시 브라우저 로컬 체험 완료 저장

비로그인 상태에서 하지 않는 것:

- 미션 진척 증가
- 미션 보상 지급
- 코인·왕관 지급
- 랭킹점수 지급
- 미니보스 진입
- 서버 사용자의 `missions` 수정

일반 회원가입 후 체험 진도가 서버로 이전되더라도, 과거 게스트 행동을 데일리 미션 진척으로 소급 적용하지 않는다.

소셜 가입의 체험 진도 이전은 별도 보완 대상이며, 연결하더라도 미션 소급 지급과는 분리한다.

# Part F. 보상 수령

## 15. 수동 수령

모든 현재 미션은 수동 수령이다.

```text
진척 goal 도달
  ↓
홈 MissionWidget에서 완료 표시
  ↓
수령하기 활성화
  ↓
POST /missions/claim
  ↓
서버 재검증
  ↓
보상 지급
  ↓
claimed 상태 저장
```

서버 검증:

- 존재하는 미션 ID인가
- 현재 기간 미션인가
- 목표를 달성했는가
- 이미 수령했는가
- 보상 정의가 유효한가
- 사용자 갱신이 원자적으로 성공했는가

클라이언트가 보내는 보상 수량은 신뢰하지 않는다. 서버가 `missions.json`에서 보상을 읽어야 한다.

---

## 16. 보상 변환

현재 `reward.xp`는 레거시 이름이지만 실제 지급은 다음처럼 처리된다.

```text
reward.xp
  ├─ 코인 증가
  └─ 누적 랭킹점수 증가
```

예:

```text
d_quiz3 reward.xp = 300
→ coin +300
→ ranking xp +300
```

현재 미션은 GP를 지급하지 않는다.

필드 이름을 `coin`으로 바꾸려면 다음을 동시에 처리해야 한다.

- 기존 JSON 호환
- 백엔드 보상 파서
- 프론트 표시
- 테스트
- 운영 데이터·문서

단순 일괄 치환은 금지한다.

---

## 17. 중복 지급 방지

필수 조건:

- 미션 완료 여부와 수령 여부를 분리
- 같은 기간의 동일 미션은 한 번만 수령
- 보상 증가와 claimed 기록을 한 원자적 갱신으로 처리
- 동시 요청에서 둘 다 성공하지 않도록 서버에서 잠금·조건 검증
- 응답 재시도에도 재지급되지 않음

대표 공격 시나리오:

```text
수령 버튼 빠르게 연타
동일 POST 병렬 전송
응답 타임아웃 후 재전송
서로 다른 브라우저에서 동시 수령
과거 기간 mission_id 재전송
클라이언트가 reward 수량 조작
```

모두 서버에서 차단해야 한다.

## 18. 홈 MissionWidget

- 현재 진척
- 목표
- 보상
- 완료 여부

|---|---|

| 로딩 | 중복 클릭 차단 |

## 19. 홈 탭 빨간 점

수령 가능한 미션이 하나 이상 있으면 홈 탭에 알림 점을 표시한다.

조건:

```text
progress >= goal
AND mission_id not in claimed
```

프론트 캐시만으로 고정하지 않고 사용자·미션 상태 재조회 후 갱신한다.

---

## 20. 수령 결과 UX

수령 성공:

- 지급된 보상 안내
- 사용자 재화 상태 갱신
- 해당 미션을 수령 완료로 변경
- 홈 탭 빨간 점 재계산

수령 실패:

- 중복 수령이면 이미 수령됨 안내
- 기간 만료면 최신 미션 새로고침
- 네트워크 오류면 재화가 실제 지급됐는지 서버 상태 재조회
- 버튼 연타 방지 잠금 해제

# Part H. 테스트

## 21. 정의 검증

- [ ] 미션 ID가 전체에서 고유하다.
- [ ] `goal`은 1 이상의 정수다.
- [ ] 지원하지 않는 보상 키가 없다.
- [ ] 이벤트 이름이 실제 발생 코드와 일치한다.
- [ ] 프론트가 모든 현재 보상 타입을 표시한다.

---

## 22. 기간 테스트

- [ ] KST 23:59와 00:00 경계를 검증한다.
- [ ] 일요일·월요일 ISO 주차 전환을 검증한다.
- [ ] 연말·연초 ISO year 전환을 검증한다.
- [ ] 데일리 초기화가 위클리를 지우지 않는다.
- [ ] 위클리 초기화가 데일리를 지우지 않는다.
- [ ] 같은 날 여러 로그인은 1일만 인정한다.

---

## 23. 이벤트 테스트

- [ ] 일반 스테이지 클리어만 `stage_clear`를 올린다.
- [ ] 비로그인 체험은 미션을 올리지 않는다.
- [ ] 복습 완료 성공 시에만 `review_done`을 올린다.
- [ ] 유닛보스·엔드보스 인정 클리어만 `boss_clear`를 올린다.
- [ ] 미니보스가 `w_boss2`에 잘못 포함되지 않는다.
- [ ] 실제 AI 텍스트 생성 성공 시에만 `ai_feedback`을 올린다.
- [ ] 실패·fallback·캐시 조회는 `ai_feedback`을 올리지 않는다.

---

## 24. 수령 테스트

- [ ] 목표 미달 수령을 거부한다.
- [ ] 정상 수령 시 정확한 보상을 지급한다.
- [ ] 같은 미션 두 번째 수령을 거부한다.
- [ ] 병렬 수령 요청에서 한 번만 지급한다.
- [ ] 클라이언트가 조작한 보상 수량을 무시한다.
- [ ] 기간 변경 뒤 과거 미션 수령을 거부한다.
- [ ] 응답 실패 후 재조회해 실제 지급 상태와 UI가 일치한다.

# AI-MON 엔드보스 설계

> 초급·중급·고급 코스의 최종 종합전, 코스 승급, 진화와 인증 보상을 담당하는 엔드보스 구현 기준

---

## 0. 문서 목적

이 문서는 다음을 정의한다.

- 엔드보스 해금과 레벨 사다리
- 코스별 프로젝트
- Phase 1~3 전투 구조
- HP·문제 수·페이즈 전환 규칙
- 서버 권위 전투 세션
- 도전 비용과 보상
- 문제 출제와 재도전 정책
- 프론트·백엔드 API 계약
- 진화와 코스 승급
- 회귀 테스트와 배포 전 검수 기준

문서와 구현이 충돌하면 아래 코드와 데이터를 우선한다.

```text
backend/routers/endboss.py
backend/routers/battle_session.py
backend/data/endboss/
frontend/src/pages/EndBoss/
```

## 2. 서비스 내 역할

```text
Unit 1~8 학습
  ↓
Unit 8 유닛보스 클리어
  ↓
엔드보스 해금
  ↓
코스별 프로젝트 선택
  ↓
Phase 1: 기본 구현·출력 이해
  ↓
Phase 2: 오류 분석·수정
  ↓
Phase 3: 최종 구현 문제
  ↓
서버 세션 status=won
  ↓
클리어 처리
  ├─ 코인·랭킹점수·왕관
  ├─ 칭호
  ├─ 진화 단계 상승
  ├─ 다음 코스 승급
  └─ 인증 상태 갱신
```

엔드보스는 단순 보스전이 아니라 코스 완료와 다음 코스 진입을 연결하는 승급 관문이다.

# Part A. 해금과 레벨 사다리

## 3. 레벨 상태

| 상태 | 의미 | 진입 |
|---|---|---|
| `cleared` | 해당 코스 엔드보스 클리어 | 가능 |
| `recognized` | 레벨 테스트 배치보다 낮은 코스 | 가능 |
| `current` | 현재 진행 코스 | 해금 조건 충족 시 가능 |
| `locked` | 아직 해금되지 않은 상위 코스 | 불가 |

선택 가능한 코스는 다음 합집합으로 결정한다.

```text
엔드보스 클리어 이력으로 열린 코스
+
현재 course_level 이하 코스
```

예:

```text
course_level = intermediate
endboss_cleared_levels = []
```

| 코스 | 상태 |
|---|---|
| beginner | `recognized` |
| intermediate | `current` |
| advanced | `locked` |

---

## 4. 현재 코스 해금

현재 코스 엔드보스 해금 조건:

```text
max_unlocked_unit[course_level] > 8
```

즉, 해당 코스 Unit 8 유닛보스를 클리어해 다음 해금 유닛 값이 9 이상이어야 한다.

해금 판단은 프론트 로컬 상태가 아니라 서버 사용자 상태를 기준으로 한다.

---

## 5. 하위 코스 인정 진입

레벨 테스트 결과가 중급 또는 고급인 사용자는 하위 코스 엔드보스에 직접 진입할 수 있다.

예:

- 중급 배치 사용자 → 초급 엔드보스 `recognized`
- 고급 배치 사용자 → 초급·중급 엔드보스 `recognized`

하위 코스의 모든 Unit 1~8을 강제로 완료시키는 정책은 아니다.

---

## 6. 재도전

이미 클리어한 코스도 재도전할 수 있다.

재도전 시:

- 왕관 도전 비용은 현재 시작 정책을 따른다.
- 최초 클리어 보상은 다시 지급하지 않는다.
- 칭호·진화·승급을 중복 지급하지 않는다.
- 전투 세션은 새로 발급한다.
- 문제 선택은 unseen 우선 정책을 따른다.

| `contact` | 연락처 앱 |
| `log_parser` | 로그 파서 |
| `weather` | 날씨 API 클라이언트 |

### 고급

| ID | 표시명 |
|---|---|

| `langchain_bot` | LangChain RAG 봇 |

문제 풀은 아래 조합으로 결정한다.

```text
course_level + project + phase
```

다른 프로젝트의 문제를 현재 프로젝트의 최소 수량 검증에 합산하지 않는다.

---

## 8. 데이터 파일

```text
backend/data/endboss/
├─ beginner.json
├─ intermediate.json
└─ advanced.json
```

과거 `finalboss/` 경로는 현재 기준이 아니다.

일부 문제의 `quiz_category`는 레거시 값 `final_boss`를 유지한다. 경로·API·화면 용어는 `endboss`다.

---

## 9. 문제 객체

```json
{
  "question_id": "endboss_beg_account_p1_001",
  "quiz_category": "final_boss",
  "is_boss": true,
  "project": "account",
  "phase": 1,
  "stage": "final",
  "unit": 9,
  "course_level": "beginner",
  "difficulty": "medium",
  "type": "output_select",
  "question": "문제 본문",
  "options": ["A", "B", "C", "D"],
  "answer": "B",
  "explanation": "해설"
}
```

필수 식별값:

- `question_id`
- `course_level`
- `project`
- `phase`
- `type`
- `question`
- `answer`

`question_id`는 전체 엔드보스 데이터에서 고유해야 한다.

---

## 10. 프로젝트별 최소 문제 수

전투 시작 전 현재 프로젝트에 다음 수량이 있어야 한다.

| Phase | 최소 문제 수 |
|---|---:|
| Phase 1 | 5 |
| Phase 2 | 4 |
| Phase 3 | 3 |

Phase 3는 최대 3회 시도를 보장해야 하므로 최소 3문제가 필요하다.

수량 검증은 아래 작업보다 먼저 수행한다.

```text
왕관 차감
seen_questions 변경
battle_token 발급
battle_session 생성
```

데이터가 부족하면 전투를 시작하지 않고 사용자 상태를 변경하지 않는다.

## 12. 중급 문제 데이터 정규화

중급 문제 데이터는 과거 구조와 현재 구조가 섞여 있을 수 있다.

로드 시 정규화 대상 예:

- `options` 누락
- 답안 키 이름 차이
- 코드블록 줄 번호 표기 차이
- 문자열 정답과 허용 답안 배열 차이
- `code_input` 테스트 정보 위치 차이

원칙:

- 데이터 로더에서 호환 가능한 범위를 정규화한다.
- 채점 전에 정규화된 내부 구조만 사용한다.
- 원본 JSON을 읽는 모든 경로가 같은 정규화 함수를 사용한다.
- 프론트에서 문제별 예외 처리를 누적하지 않는다.
- 정규화 실패 문제는 시작 전 데이터 검증에서 제외하거나 오류로 처리한다.

# Part C. 전투 구조

## 13. 전체 흐름

```text
POST /boss/endboss/start
  ↓
서버 세션 생성
  ↓
Phase 1 문제 5개
  ↓
Phase 2 문제 4개
  ↓
총 9정답으로 boss_hp=0
  ↓
Phase 3 최대 3회
  ↓
정답이면 status=won
  ↓
POST /boss/endboss/clear
  ↓
보상 지급
  ↓
세션 consume
```

최대 문제 수:

```text
5 + 4 + 3 = 12
```

---

## 14. 초기 HP와 피해

```text
boss_hp = 1800
player_hp = 1200
```

정답:

```text
boss_hp -= 200
```

오답:

```text
player_hp -= 400
```

Phase 1~2의 9문제를 모두 맞히면:

```text
1800 - (200 × 9) = 0
```

플레이어는 오답 3회면 HP가 0이 된다.

```text
1200 - (400 × 3) = 0
```

---

## 15. Phase 1

- 5문제를 출제한다.
- 정답마다 보스 HP를 200 감소시킨다.
- 오답마다 플레이어 HP를 400 감소시킨다.
- 플레이어 HP가 0 이하가 되면 패배다.
- 5문제 처리 뒤 생존하면 Phase 2로 이동한다.

---

## 16. Phase 2

- 4문제를 출제한다.
- 피해 규칙은 Phase 1과 동일하다.
- Phase 1~2 총 9문제를 전부 맞혀야 보스 HP가 0이 된다.
- 보스 HP가 0이 되어도 즉시 최종 승리 보상을 지급하지 않는다.
- Phase 3 최종 구현 문제를 통과해야 세션이 `won` 상태가 된다.

---

## 17. Phase 3

- 최대 3개의 서로 다른 문제를 순차적으로 사용한다.
- 정답이면 즉시 `status=won`.
- 오답이면 다음 Phase 3 문제로 이동한다.
- 최대 시도를 모두 실패하면 패배 처리한다.
- 같은 요청 재전송으로 다음 문제가 건너뛰지 않도록 서버 세션에서 제출 상태를 확인한다.
- Phase 3 문제 수가 3개 미만이면 전투 시작 자체를 거부한다.

---

## 18. 승패 우선순위

한 제출로 보스와 플레이어 HP가 동시에 임계값에 도달할 수 있는 구조를 만들지 않는 것이 우선이다.

판정은 서버의 명시적 순서를 따른다.

1. 현재 세션·문제·제출 가능 상태 검증
2. 답안 채점
3. 피해 적용
4. 플레이어 패배 조건 확인
5. 페이즈 전환 조건 확인
6. Phase 3 정답 시 승리 상태 설정
7. 응답 저장

클라이언트 애니메이션 순서로 승패를 결정하지 않는다.

# Part D. 서버 권위 세션

## 19. 세션 목적

서버 세션은 다음 조작을 차단한다.

- 클라이언트 HP 변조
- 문제 순서 조작
- 답안 없이 clear 호출
- 승리하지 않은 전투의 보상 요청
- 동일 세션 중복 보상
- 다른 프로젝트·코스 값으로 제출
- 만료 세션 재사용

---

## 20. 세션 핵심 상태

세션에 포함되는 개념 값:

- 사용자 ID
- 세션 또는 배틀 토큰
- `course_level`
- `project`
- 현재 `phase`
- 현재 문제
- Phase별 문제 목록
- 제출 완료 문제
- `boss_hp`
- `player_hp`
- `status`
- 시작·갱신·만료 시각
- 보상 consume 여부

상태 예:

```text
active
won
lost
consumed
expired
```

실제 상수명은 코드 구현을 따른다.

---

## 21. 제출 검증

답안 제출 전 서버 확인:

- 세션이 존재하는가
- 현재 사용자 소유인가
- 만료되지 않았는가
- `active` 상태인가
- 요청 문제 ID가 현재 문제와 일치하는가
- 이미 제출한 문제가 아닌가
- 요청 코스·프로젝트가 세션과 일치하는가

하나라도 실패하면 전투 상태를 변경하지 않는다.

---

## 22. 중복 제출 방지

프론트:

- `handleSubmit` 진입 즉시 ref lock
- 응답 전 버튼 비활성
- 같은 문제 연속 클릭 차단

서버:

- 현재 문제 ID 검증
- 이미 처리된 제출 여부 검증
- 세션 원자적 갱신
- 응답 재전송에도 피해를 두 번 적용하지 않음

프론트 잠금은 UX 보호이고, 최종 방어는 서버다.

---

## 23. 세션 정리

종료·만료 세션은 주기적으로 정리한다.

JSONB 상태에서 키를 삭제할 때 단순 merge만 사용하면 기존 키가 남을 수 있다.

안전한 방식:

```text
현재 battle_sessions 전체 로드
→ 만료·종료 키 제거
→ 정리된 전체 객체 저장
```

세션 정리 작업은 보상 consume 상태를 보존해야 한다.

# Part E. 시작과 비용

## 24. 시작 검증 순서

```text
1. 로그인 사용자 확인
2. course_level·project 유효성
3. 코스 접근 권한·해금 확인
4. 프로젝트별 Phase 1~3 문제 수 확인
5. 왕관 3개 이상 확인
6. 문제 선택
7. 왕관 3개 차감
8. battle_session 생성
9. 첫 문제 응답
```

문제 데이터 부족이나 권한 오류가 있으면 왕관을 차감하지 않는다.

---

## 25. 도전 비용

```text
왕관 3개
```

비용은 `/start` 성공 시 한 번 차감한다.

차감 후 세션 생성에 실패하는 부분 실패가 발생하지 않도록 원자성 또는 보상 복구 처리가 필요하다.

클라이언트가 왕관 값을 직접 감소시키지 않는다. 서버 응답 뒤 사용자 상태를 갱신한다.

---

# Part F. 문제 선택과 재도전

## 26. unseen 우선

문제 선택 기본 정책:

```text
현재 course_level + project + phase 풀
  ↓
사용자 seen_questions 제외
  ↓
남은 unseen 문제 랜덤 셔플
  ↓
필요 수량 선택
```

unseen이 부족하면:

```text
전체 풀에서 이미 선택된 문제 제외
  ↓
랜덤 보충
```

풀 전체가 소진된 이후에는 재출제를 허용한다.

---

## 27. 실제 랜덤

문제 데이터 원본 순서대로 앞에서 자르는 방식은 사용하지 않는다.

필요 조건:

- 시작할 때 셔플
- 프로젝트별 독립 풀
- Phase별 독립 풀
- 동일 전투 안 중복 금지
- 가능하면 재도전 간 unseen 우선

테스트에서는 랜덤 결과 자체보다 다음 불변식을 검증한다.

- 수량 충족
- 프로젝트 혼입 없음
- Phase 혼입 없음
- 동일 전투 중복 없음
- unseen 우선

---

## 28. seen 상태 저장

seen 문제 상태는 사용자별로 유지한다.

주의:

- 문제 수 검증 전에 seen 상태를 변경하지 않는다.
- 전투 시작 실패 시 seen이 증가하면 안 된다.
- 프로젝트·코스·Phase 구분 없이 하나의 거대한 키로 충돌하지 않도록 한다.
- 문제 ID 변경은 기존 seen 이력과 호환성에 영향을 준다.

# Part G. 채점

## 29. 객관식·출력·에러 찾기

다음 유형의 오답은 정적 피드백으로 즉시 처리한다.

- `multiple_choice`
- `output_select`
- `error_find`

이 유형의 오답마다 LLM을 동기 호출하지 않는다.

응답에 포함할 수 있는 값:

- 정답 여부
- 정답
- 해설
- 현재 HP
- 다음 문제·페이즈
- 세션 상태

---

## 30. 빈칸·코드 입력

- `fill_in_blank`
- `code_input`

문제 정의와 서버 채점 정책에 따라 정규화·테스트·LLM 채점을 사용할 수 있다.

원칙:

- 가능한 결정적 채점을 우선한다.
- 문자열 공백·줄바꿈 정규화 범위를 명시한다.
- 여러 허용 답안은 서버 데이터로 관리한다.
- LLM 응답만으로 전투 승패를 확정할 때는 JSON 파싱과 fallback을 방어한다.
- 채점 실패를 정답 또는 승리로 간주하지 않는다.
- 동일 제출 재시도로 비용과 피해가 중복되지 않게 한다.

# Part H. 승리와 보상

## 31. 승리 조건

최종 보상 가능한 상태:

```text
battle_session.status == "won"
```

프론트에서 보스 HP가 0으로 보이는 것만으로 clear를 승인하지 않는다.

`/clear`는 서버 세션을 다시 확인한다.

---

## 32. 최초 클리어 보상

코스별 최초 클리어:

- 코인 15,000
- 누적 랭킹점수 15,000
- 왕관 15
- 코스별 칭호
- 진화 단계 갱신
- 다음 코스 승급
- 인증 상태 갱신

GP는 지급하지 않는다.

보상 수량은 클라이언트 요청값이 아니라 서버 상수·정책에서 결정한다.

---

## 33. 중복 방지

두 단계 방어:

1. `endboss_cleared_levels`
2. 배틀 세션 consume

처리 순서:

```text
won 세션 확인
→ consumed 여부 확인
→ 해당 코스 최초 클리어 여부 확인
→ 최초 보상·진화·승급 적용
→ cleared_levels 기록
→ 세션 consume
→ 응답
```

동시 clear 요청에서도 한 번만 지급되어야 한다.

이미 클리어한 코스 재도전 승리는 전투 완료로 표시할 수 있지만 최초 클리어 보상은 없다.

---

## 34. 진화

| 클리어 코스 | 진화 단계 |
|---|---:|
| beginner | 1 |
| intermediate | 2 |
| advanced | 3 |

진화 단계는 감소하지 않는다.

이미 더 높은 진화 단계인 사용자가 하위 코스를 클리어해도 낮아지면 안 된다.

---

## 35. 코스 승급

대표 흐름:

```text
beginner 클리어
→ intermediate 진입 가능

intermediate 클리어
→ advanced 진입 가능

advanced 클리어
→ 최종 코스 완료 상태
```

승급은 사용자 `course_level`, 해금 상태, 엔드보스 클리어 이력을 일관되게 갱신해야 한다.

하위 코스 `recognized` 클리어가 현재 더 높은 코스를 낮추면 안 된다.

---

## 36. 칭호와 인증

코스별 엔드보스 최초 클리어 시 해당 칭호를 부여한다.

요구 사항:

- 같은 칭호 중복 저장 방지
- 이미 획득한 칭호 보존
- 프로필·인증 화면과 동기화
- 재도전으로 중복 알림·보상 방지

정확한 칭호 문자열은 현재 서버 상수 또는 데이터 정의를 따른다.

# Part I. API 계약

## 37. 레벨 상태 조회

목적:

- 코스별 `cleared`, `recognized`, `current`, `locked`
- 해금 여부
- 프로젝트 선택 가능 여부
- 최초 보상 여부

응답 값은 서버 사용자 상태로 계산한다.

---

## 38. 시작

```text
POST /boss/endboss/start
```

요청 개념값:

```json
{
  "course_level": "beginner",
  "project": "account"
}
```

응답 개념값:

```json
{
  "battle_token": "...",
  "course_level": "beginner",
  "project": "account",
  "phase": 1,
  "boss_hp": 1800,
  "player_hp": 1200,
  "question": {}
}
```

정답 원본은 공개하지 않는다.

---

## 39. 답안 제출

요청 개념값:

```json
{
  "battle_token": "...",
  "question_id": "...",
  "answer": "..."
}
```

응답 개념값:

```json
{
  "correct": true,
  "explanation": "...",
  "boss_hp": 1600,
  "player_hp": 1200,
  "phase": 1,
  "status": "active",
  "next_question": {}
}
```

세션이 `won` 또는 `lost`면 다음 문제를 제공하지 않는다.

---

## 40. 클리어

```text
POST /boss/endboss/clear
```

서버 확인:

- 세션 소유자
- `status == "won"`
- 미소비 상태
- 코스·프로젝트 일치
- 최초 클리어 여부

응답 개념값:

- 최초 클리어 여부
- 지급 보상
- 새 재화
- 진화 단계
- 코스 승급
- 칭호
- 인증 상태

---

## 41. 레거시 토큰 호환

구형·신형 `battle_token` 스키마를 동시에 읽는 호환 경로가 존재할 수 있다.

원칙:

- 새 세션은 현재 표준으로 생성한다.
- 구형 토큰은 명시된 범위에서만 읽는다.
- 호환 fallback이 세션 소유권·승리 검증을 우회하면 안 된다.
- 호환 제거 전 운영 중인 오래된 세션의 만료를 확인한다.

5. 최초 클리어 보상과 전체 경제 밸런스를 사용자 증가 후 재검토
